Core Architecture & Principles

Foundational architectural decisions defining the simulation engine boundary, clock model, and memory layout.

Engine-as-Spine Architecture

#
architecturespinetenet

The simulation VM is main() and owns the master clock, entities, and state, treating graphics engines strictly as peripherals.

pub fn main() !void { var world = World.init(...); var vm = VM.init(...); while (running) { vm.step_tick(); bridge.capture_frame(); } }

What it does

Inverts the traditional game engine model: rather than embedding a scripting language as a guest plugin inside Unity or Godot, BeSpoke is the host spine that owns simulation state, rules, pathfinding, and narrative logic, publishing read-only render frames to peripheral presentation layers.

How it works

  1. src/main.zig drives the master simulation loop, allocating the World arena and SpatialSystem.
  2. The Virtual Machine steps discrete simulation ticks at a fixed frequency (e.g. 20 Hz or 60 Hz).
  3. DisplayBridge captures double-buffered snapshot frames (RenderFrame) containing entities, waypoints, and dialogue.
  4. Peripheral display renderers (like SDL2 or headless runners) read double-buffered frames and deliver input intents as UserAction events.

Why it works this wayrecorded

Embedded scripting plugins in commercial game engines suffer from frame-rate dependent logic bugs, garbage collection spikes, non-deterministic state serialization, and tight coupling to rendering backends. Owning the spine ensures 100% deterministic, headless testability and seamless time-travel rewind.

Discrete Simulation Tick Clock

#
timingdeterminismsimulation

Simulation state advances strictly in integer ticks without floating-point delta accumulation.

pub fn step_tick(self: *VM) !void { self.world.current_tick += 1; ... }

What it does

Governs all motor movement, TTL fact expirations, fiber waits, and reactive rule edges using integer tick counters rather than floating-point delta seconds (dt).

How it works

  1. VM.step_tick() increments World.current_tick by 1 on each discrete simulation step.
  2. Fact TTLs decay by integer ticks and are automatically pruned when current_tick exceeds expires_at_tick.
  3. Fibers suspended via wait_ticks or wait_until wake up when the integer tick target is met.
  4. Visual renderers interpolate fractional positions between consecutive ticks for smooth 60 Hz screen motion.

Why it works this wayrecorded

Floating-point delta time introduces accumulation errors, platform-dependent rounding discrepancies, and non-deterministic divergence that destroys replayability and networking. Integer ticks make simulation states bit-for-bit identical across runs.

Contiguous Arena Allocation & Zero Raw Pointers

#
memoryperformanceserialization

World state is stored in a contiguous byte arena with zero internal pointers, enabling instant memcpy snapshots.

pub const World = struct { arena: std.heap.ArenaAllocator, facts: std.MultiArrayList(Fact), ... }

What it does

Houses all simulation entities, relations, and fact rows in contiguous array allocations, referencing entities and strings by integer handles rather than raw virtual memory addresses.

How it works

  1. World initializes an arena allocator with a fixed reserve (e.g. 1 MB).
  2. Facts are stored in Structure-of-Arrays layout via std.MultiArrayList(Fact) with subject, relation, object, and expires_at columns.
  3. Entities are typed 32-bit handles (EntityId) indexing interned string tables.
  4. Serialization (save_state and restore_state) writes and reads raw memory buffers with CRC32 checksums.

Why it works this wayrecorded

Raw pointers break across processes, prevent binary snapshot persistence, and cause cache misses during bulk queries. Contiguous array arenas maximize CPU cache line locality and allow instant memory rewind with zero deserialization overhead.

Zero External Dependencies Policy

#
dependenciestoolchainportability

The core simulation runtime, compiler, and VM require zero external C or package dependencies beyond pure Zig.

build.zig: exe = b.addExecutable(.{ .name = "bespoke", .root_source_file = b.path("src/main.zig") });

What it does

Guarantees that the compiler, relational database, bytecode VM, pathfinding, and REPL build and run out-of-the-box on any Linux, macOS, or Windows target with only the Zig 0.13+ compiler.

How it works

  1. The compiler front-end uses custom recursive-descent lexing and Pratt parsing written from scratch.
  2. Display rendering optionally links SDL2 as a peripheral consumer, but falls back seamlessly to headless terminal mode if unavailable.
  3. Documentation tools rely exclusively on the Python 3 standard library.

Why it works this wayrecorded

Heavy third-party package dependencies create fragile build pipelines, security supply chain risks, and platform incompatibilities. Zero-dependency design keeps BeSpoke lean, auditable, and easily embeddable.

Flat 4-Tuple Relational Facts

#
factsrelationalstate

World state is composed of relational rows: (subject, relation, object, expires_at_tick).

pub const Fact = struct { subject: EntityId, relation: RelationId, object: i32, expires_at: u64 };

What it does

Replaces traditional object-oriented properties and component hierarchies with flat relational fact tuples representing systemic knowledge, inventory possession, spatial co-location, and emotional states.

How it works

  1. Facts are asserted via World.remember(subject, relation, object, ttl_ticks).
  2. Facts are retracted via World.forget(subject, relation, object).
  3. TTL decay: when ttl_ticks > 0, expires_at is set to current_tick + ttl_ticks.
  4. Pruning: World.prune_expired() scans the facts list at the start of each tick, recording expired rows into a recently_expired ring buffer for expiration hooks.

Why it works this wayrecorded

OOP class hierarchies create rigid coupling where adding a new emergent interaction requires modifying multiple classes. Relational facts decouple subjects from attributes, enabling dynamic pattern queries without schema migrations.

Functional Single-Value Property Overwrite

#
relationsfunctionalproperties

Relations marked as functional auto-overwrite previous values on assertion.

const carries = try world.intern_relation("Carries", .set); try world.remember(actor, carries, item, 0);

What it does

Distinguishes between multi-valued relations (e.g. FriendsWith, KnowsSecret) and single-valued functional properties (e.g. Carries, CurrentRoom, Health), automatically retracting old values when a new value is remembered.

How it works

  1. Relations are registered with RelationKind (.set for functional single-value, .bag for multi-value).
  2. When World.remember is called on a .set relation, World scans for any existing fact matching (subject, relation, _) and overwrites its object and expiry in place.
  3. Ensures an entity cannot simultaneously occupy multiple rooms or hold mutually exclusive single states.

Why it works this wayrecorded

Without functional auto-overwrite, script authors would be forced to manually write pair-wise forget statements before every state change, introducing subtle desynchronization bugs when forgetting is overlooked.

CRC32 Snapshots & Time-Travel Rewind

#
time-travelsnapshotsrewind

Instantaneous serialization and deserialization of complete simulation state with CRC32 integrity checks.

try world.save_state(writer); ... try world.restore_state(reader);

What it does

Captures the entire relational world state into an in-memory byte buffer on each tick, allowing players and developers to scrub backward or forward across history instantaneously.

How it works

  1. World.save_state serializes tick count, interned entity names, relations, and fact columns, appending a CRC32 checksum.
  2. World.restore_state verifies the CRC32 checksum, clears the current arena, and restores memory in-place.
  3. DisplayBridge captures a fresh render frame immediately after restore to synchronize peripheral visualization.
  4. When simulation advances after scrubbing into the past, divergent future snapshots are automatically pruned.

Why it works this wayrecorded

Debugging systemic simulation bugs requires reproducing non-deterministic edge cases. Snapshot rewind lets developers scrub directly to the tick where a state transition occurred, inspect facts, and test alternative actions.

Bytecode Instruction Set & Stack Machine

#
vmbytecodeopcodes

Compact stack-based virtual machine executing variable-length bytecode chunks.

pub const Opcode = enum(u8) { push_const, remember, forget, wait_ticks, call_routine, emit_cue, halt, ... };

What it does

Executes compiled BeSpoke programs via a compact bytecode interpreter supporting constants, relational mutations, math, routine calls, cues, and control flow.

How it works

  1. BytecodeChunk stores an array of byte opcodes and a pool of 32-bit constants.
  2. VM evaluates instructions using an operand stack per fiber.
  3. Relational opcodes (op_remember, op_forget, op_query) operate directly on the World database.
  4. Execution is bounded per tick by max_steps_per_fiber to prevent runaway loops from freezing the engine.

Why it works this wayrecorded

Direct AST evaluation has poor cache locality and high tree-walking overhead. A flat bytecode chunk executes in a tight loop and allows serialization of fiber instruction pointers.

Cooperative Fiber Scheduler & Temporal Suspension

#
fibersschedulerconcurrency

Fiber-based routine execution suspended across ticks via wait_ticks and wait_until.

pub const Fiber = struct { id: FiberId, entity: EntityId, ip: usize, wait_ticks: u32, ... };

What it does

Executes actor routines concurrently within a single simulation thread using lightweight fibers that yield voluntarily when waiting for time or events.

How it works

  1. VM maintains an active list of Fiber descriptors, each with its own instruction pointer, call stack, and operand stack.
  2. Instructions like wait_ticks set fiber.wait_ticks, suspending the fiber until the specified tick delay elapses.
  3. wait_until evaluates a relational condition pattern each tick and resumes when satisfied.
  4. On each simulation tick, VM steps all active, non-waiting fibers up to their yield points.

Why it works this wayrecorded

Operating system threads introduce non-deterministic race conditions, locks, and heavy memory overhead. Cooperative fibers are 100% deterministic, pause with zero CPU cost, and can be serialized cleanly.

Cue Event Dispatch & Priority Interruption

#
cueseventsinterrupts

Discrete event cues trigger routine fibers with priority-tiered preemption stacks.

vm.fire_cue(compiled, "Uses", actor, target_a, target_b);

What it does

Delivers external player interactions and systemic world events to registered cue handlers, preempting lower-priority routines and cleanly resuming them upon completion.

How it works

  1. Cues are emitted via VM.fire_cue, which looks up matching entry points in CompiledProgram.cue_handler_entries.
  2. When an interrupt occurs (e.g. thief alert), the entity's active fiber is pushed onto an interrupt stack.
  3. The higher-priority handler executes to completion.
  4. Opcode resume_routine pops the interrupted fiber state, restoring its instruction pointer and continuing its original routine.

Why it works this wayrecorded

Standard event callbacks discard context, forcing actors to restart tasks from scratch after an interruption. Priority stacks let NPCs react urgently to emergencies and then smoothly resume their previous actions.

Requiring narrative designers to author two identical script handlers for every combination is error-prone and redundant. Built-in commutativity guarantees symmetric interaction.

Waypoint Node Graphs & Topological Pathfinding

#
spatialwaypointspathfindinga-star

Spatial environments are modeled as discrete 2D waypoint graphs with A* shortest-path routing.

pub const WaypointGraph = struct { waypoints: std.ArrayList(Waypoint), edges: std.ArrayList(Edge), ... };

What it does

Defines rooms and navigable ground locations as integer-coordinate waypoint nodes connected by bidirectional edges, calculating walking paths via discrete A* search.

How it works

  1. SpatialGraph stores waypoints with room IDs, integer coordinates (x, y), and names.
  2. Edges represent unobstructed walking paths between waypoints.
  3. SpatialGraph.find_path computes the shortest sequence of waypoints using Manhattan/Euclidean integer heuristics.
  4. Actors traverse edges step-by-step at discrete velocities.

Why it works this wayrecorded

Continuous 3D physics sandboxes require complex collision meshes and floating-point math that destroy determinism. Topological waypoint graphs fit narrative graphic adventures perfectly and compute in sub-microsecond time.

Actor Standoff Separation & Non-Overlapping Labels

#
layoutstandoffrenderinglabelscollision-avoidance

Automated 60px horizontal separation, priority-based 2D text layout solver, and standardized scale hierarchy prevent label collision.

pub const TextLayoutResolver = text_layout.TextLayoutResolver;
pub fn get_entity_screen_layout(idx: usize, entities: []const RenderEntity, w: i32, h: i32) EntityScreenLayout

What it does

Solves the visual crowding problem when multiple actors occupy the exact same waypoint or proximate stage marks by combining actor horizontal standoff spacing with a centralized 2D collision-avoidance label layout engine.

How it works

  1. get_entity_screen_layout groups entities within 32 pixels into a spatial cluster and spreads them horizontally by ±30px.
  2. TextLayoutResolver collects all floating in-world labels (actor names, status badges, waypoint names, hotspot prompts) and registers actor and waypoint tokens as physical obstacles.

Why it works this wayrecorded

In theater and adventure scenes (e.g. Guybrush and Organiser at the Starting Line, or George and Billy Goat at Lochmarne), actors frequently gather at proximate marks. Drawing labels at fixed coordinates produces illegible text overlap. Centralized collision resolution guarantees every string a legible, collision-free slot.

Discrete Grid Overlay

#
gridspatialcellshazards

An optional per-room grid whose cell attributes and fire, smoke, and water automata live in World facts.

grid <Name> in <Room>:  size W H  cell N  [origin X Y]  flammable|liquid|blocking x y [w h]  place <Mark> x y

What it does

Overlays a room with a discrete grid of cells carrying flammable, liquid, and blocking attributes, and maps each waypoint to the cell under its position.

How it works

  1. src/grid.zig defines Grid geometry (room, width, height, cell size, origin); SpatialSystem.grids holds at most one overlay per room.
  2. Each set attribute is a CellFlammable, CellLiquid, or CellBlocking fact on the grid entity whose value is the cell index y*W+x; empty cells have no facts.
  3. A grid script declaration compiles into CompiledProgram.grids; host.initialize_subsystems seeds the layout once and marks it with GridSeeded.
  4. place moves a mark to a cell centre and refreshes its edge costs; SpatialSystem.waypoint_blocked treats a blocking cell like WaypointBlocked for world-aware walks.
  5. .bspk version 7 stores grids; versions 1 through 6 load without them.
  6. Rates burn, spread, dissipate, and flow drive grid.step each host.tick: fires are CellBurning facts whose TTL is their remaining burn, smoke is CellSmoke refreshed by each fire, and liquid floods non-blocking neighbours and douses fire.
